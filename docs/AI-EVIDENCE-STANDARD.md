# AI 证据驱动执行规范（AI-EVIDENCE-STANDARD）

> **性质**：**规范性** —— 约束“AI 怎么表述结论、怎么取证据、怎么裁决冲突、什么时候必须停下来”。
> **补的是哪一块**：§1.1“不确定 → 先查文档”管的是**去哪找答案**；本规范管的是**找到之后，结论怎么写才经得起第三方独立复核**。
> **不重复谁**：[`docs/WORKFLOW.md`](WORKFLOW.md) 管流程与命令；[`docs/AI-PITFALLS.md`](AI-PITFALLS.md) 管“以前栽过什么”；数据模型与统计口径见各自权威文档（索引见 [`docs/README.md`](README.md)）。
> **门禁**：`scripts/governance-rules.test.mjs`（规范存在 + 被 AI 必读入口引用 + 要素齐全 + 防形式主义）。

---

## 0. 怎么用这份规范

**读法**：§1–§3 是“结论怎么写”（最常用）；§4–§7 是“过程怎么留痕”；§8–§9 是“协作与测试”；§10 是“隐私与数据边界”；§11–§12 是“什么时候停、怎么交付”；§13 是交付前自检。

### 0.1 三档主张：已验证 / 推断 / 未知

对**会影响执行、隐私安全、数据迁移、代码正确性或最终验收**的结论，必须标出它属于哪一档：

| 标签 | 含义 | 判据（满足才算这一档） |
|---|---|---|
| **〔已验证〕** | 本轮用直接证据确认过 | 证据**可复现**：第三方照你给的路径/命令能重得同样结果 |
| **〔推断〕** | 由已验证事实推出，未直接验证 | 能指出**推断链的每一步依据**，并说清哪一步还没验 |
| **〔未知〕** | 现有信息不足 | 能写明**缺什么、谁手里有、怎么补** |

**硬规则**：

- 未验证的推断**不得**表述为事实；未知**不得**由模型补全成“看起来合理的答案”（禁止编造）。
- 证据等级**只反映真实验证程度**：**想得更久、多个 AI 意见一致、结论听起来合理，都不能提升可信度**（“人数不是证据”）。
- 未知是**合法结论**，不是失败。标〔未知〕并说清缺什么，比编一个完整答案更有用。

**占位值 ≠ 未知**：

- **占位值**（`0` / `""` / `null` / `N/A` / 默认值）表达的是**这条没算、没输入、或者当前为空** —— 它**不是**真实读数，**也不是**〔未知〕；
- 真〔未知〕不得用占位值冒充“有值”（严禁做假账或粉饰数据）；
- 交付时写清是哪一种：**真实读数 / 占位（未计算）/ 口径缺失 / 真未知（缺信息）**。

### 0.2 标注放在哪、标多少

- **只标关键结论**：普通描述、过程叙述、背景铺垫**不标**。贴满标签的文档和报告会失去可读性。
- 放法二选一：结论句尾内联 `〔已验证〕`；或结论表加一列“证据等级”。
- **一标就要带证据**：标了〔已验证〕却没给证据路径，等于没标（证据形式见 §1.2）。

### 0.3 本规范不要求什么（防形式主义）

这些**明确不做**，做了不加分、只会消耗预算：

- ❌ 不要求每句话都贴标签；
- ❌ 不要求把每次读文件、每次搜索都记录下来；
- ❌ 不要求输出大篇幅过程报告（**改了什么 + 证据 + 未决项**三段足够）；
- ❌ 不要求为了凑证据反复扫描整个仓库 —— 一次定向读 + 一次定向跑通常就够；
- ❌ 不要求把 AI 无法保证的“绝对正确”写成承诺。

**反过来**，如果你有**比本规范更好的证据形式**（更精确、更省事、同样能被第三方复核），**用你的**，但必须让复核者知道**怎么复核**。本规范约束的是**结论的可追溯性**，不是结论的写法模板。

## 1. 主张、证据与取证

### 1.1 主张的三档（补充判据）

- “已验证”是**相对于当前工作区与环境**的：换了依赖版本、未同步迁移、分支切换，结论可能就不再成立 —— 所以引用时要带**适用范围**（哪个分支、哪个 commit）。
- 历史结论（往期 Issue / PR / 旧会话）**只能算线索**；引用它们时标明“历史结论，本轮未复核”，或本轮复核后升档为〔已验证〕。

### 1.2 证据的合格形式

至少给出**一种**别人能独立复核的形式：

| 主张类型 | 合格证据 | 不合格（等于没给） |
|---|---|---|
| 代码事实 | `路径:行号` + 关键行代码摘录 | “我看过了” |
| 运行事实 | **命令原文 + 关键输出**（含退出码） | “我跑过了” |
| 测试事实 | 测试名 + `pass N, fail 0` / 失败明细 | “测试都过了” |
| 外部依赖行为 | **实际依赖版本** + 官方文档链接或真实响应片段 | 与当前版本不匹配的资料 |
| 设备或运行状态 | 可复核的测试日志、ADB 命令输出或截图 | “在真机上是正常的” |
| 历史结论 | 明确标注**本轮是否复核** | 直接当现状引用 |
| **否定性断言**（“全仓 0 处”/“不存在”） | **检索命令原文 + 检索范围**（命令模式、路径/glob、分支）+ 命中数 | “我搜过了”“就是没有” |

### 1.3 三类问题必须分开写

同一个发现可能是三种东西，在交付里混为一谈就是幻觉：

- **已复现的缺陷** —— 有触发路径、有观察到的错误行为或断言失败；
- **合理推断** —— 证据指向它，但未在真实环境看到；
- **待验证风险** —— 理论上可能，当前没有证据证明已触发。

后果断言（会导致崩溃、数据丢失、Room 升级失败）**必须能指出可达路径**（哪一行、什么输入条件）；指不出就降级为“疑似 / 需核实”，不要虚标为致命缺陷。

## 2. 证据来源与冲突裁决

### 2.1 按“问题是什么”选证据

| 你要回答的问题 | 首要证据 | 次要（不可单独采信） |
|---|---|---|
| 当前实现到底怎么跑 | 当前检出的**代码 + Room 数据库 + 配置 + 测试** | 文档描述、旧 PR 结论 |
| 预期行为应该是什么 | **用户明确口径** + 已确认的产品契约（[`PRODUCT.md`](PRODUCT.md)、ADR 等） | 代码现状（代码只说明“现在是怎样”，不说明“该怎样”） |
| 改动是否真的有效 | **定向测试 / Lint / 构建结果** | “代码看起来没毛病” |
| 外部库与 Android 行为 | **实际使用版本的官方文档 + 真实测试** | 记忆里的用法、旧版本资料 |
| 这个结论以前有人下过吗 | 旧 Issue / PR / 踩坑记录 | —— **只算线索** |

### 2.2 冲突时怎么裁

不存在“代码永远赢”或“文档永远赢”：代码可能有缺陷、测试可能不完整、文档可能定义了尚未实现的预期。按这个顺序裁：

1. **先说清争的是什么**：是“现状是什么”还是“应该是什么”？
   - 争**现状** → 当前代码 + 实测输出（文档与代码冲突时**改文档**，不改代码迁就腐化文档）；
   - 争**期望** → 用户口径 / 已确认的产品契约与 ADR（此时代码可能才是待修的一侧）。
2. **分别记下两边的说法与各自的证据**（哪两个来源、各自说了什么）。
3. **给出裁决依据**：哪条证据对这个具体问题有证明力，另一条为什么不成立。
4. **裁不了就标〔未知〕并问人**。

### 2.3 禁止事项

伪造来源、虚构引用、编造文件内容、捏造测试结果、拿与当前依赖版本不匹配的资料当确定性依据 —— **一律禁止**。另外：**不得沿用历史数值**，要报数字就现场重查并写出命令。

## 3. 下结论前的必核项

当结论涉及“某功能到底有没有生效 / Bug 到底有没有修复”时，必须核实：

**工程与 Android 向**：
1. **文件真的存在** —— 给出路径，不凭记忆；
2. **函数真的被调用** —— 声明 ≠ 在调用链上；确保调用链完整；
3. **状态真的持久化** —— UI 变更是否真正写入 Room，而非仅停留在内存状态；
4. **异常路径与边界处理** —— 协程异常是否捕获并处理，网络失败是否兜底保证离线可用；
5. **测试覆盖真实断言** —— 读断言逻辑，禁止写无断言测试或假断言（如常量等于常量）；
6. **Room 迁移与 Schema 匹配** —— 涉及表结构变更，是否更新了 `SCHEMA_VERSION`、提供了 Migration、更新了 schema 快照并跑了迁移测试；
7. **这是缺陷、推断，还是风险**（§1.3）。

**引用与收口**：
8. **断言“某提交修了 X”** ⇒ 先核对实际 diff（`git show <sha> --stat` + 关键 hunk），确认改动落在该路径；
9. **“抽出一个公共函数/组件” ≠ “唯一实现”** ⇒ 收口同一语义前先全仓搜索列清单，确保所有旧调用点均已重构接入，否则平行实现仍然存在。

## 4. 假设：可以提，但要带着验证计划

提出假设时五件事一起给：
1. **假设是什么**（一句话，可证伪）；
2. **依据**（哪些已验证事实支撑它）；
3. **还有哪些合理解释**（至少一个竞争假设）；
4. **怎么区分它们**（什么观察能证伪 A 而支持 B）；
5. **验证结果**（验证后接受 / 修正 / 否定）。

信息不足时，**优先做低风险、只读的调查**（读代码、跑测试），不随意动生产或危险配置。

## 5. 长任务：状态、交接与上下文腐化

### 5.1 载体选择（严禁新建游离 md）

- 载体使用仓库既有的：Issue（目标与验收条件）、PR 描述（范围 / 验证结果 / 未完成项）；
- **不要**每次执行都新建一份临时 md 文档；**不要**把整段聊天记录直接拷入仓库；
- 仅服务于单次任务的临时调研笔记或分析草稿，存放在 `work/` 或临时目录，**任务结束前彻底清除**。

### 5.2 恢复任务时先复核

重新接手（换会话、上下文压缩、多人协作）时，**先**：
1. 重读相关源码文件与契约；
2. 运行 `git status --short --branch` 与 `git log -5 --oneline` 检查最新基线；
3. 跑一次相关定向测试（**上一轮通过不是本轮证据**）。

## 6. 分阶段执行与阶段验收

大型任务必须拆成有清晰边界的阶段，每一阶段明确：
- **目标**：这一阶段解决什么；
- **修改范围与非目标**：动哪些文件、明确不动哪些；
- **预期产物**：代码 / 测试 / 文档；
- **验证方式**：跑什么命令、怎么算通过；
- **验收条件**：满足哪些才叫该阶段完成。

未满足验收条件的阶段，不得标记为已完成。

## 7. 修改前后的证据闭环

### 7.1 完整链路

```text
问题/需求 → 事实调查 → 问题定界 → 修改方案 → 实际改动 → 验证结果 → 最终结论
```

**改前**：
- `git status --short --branch` 确认分支；
- 识别并保护用户未提交的修改，不许覆盖或顺手提交；
- 动手前查阅权威文档与踩坑清单。

**改后**：
- 审查实际 diff：`git diff --stat` 对照本次范围，自检是否有无关夹带；
- 运行定向验证并保留真实命令与输出；
- 同步更新对应权威文档与注释。

### 7.2 测试结果必须分五态说清

| 状态 | 怎么表述 |
|---|---|
| **已执行且通过** | 命令原文 + `pass N, fail 0` / `OK` |
| **已执行但失败** | 失败明细，并分清是代码缺陷还是环境问题 |
| **尚未执行** | 明说“未执行”及具体原因 |
| **无法执行** | 明说环境/依赖原因（如缺真机、缺签名密钥）+ 已执行的替代检查 |
| **通过但覆盖不足** | 说明覆盖盲区及对结论的影响 |

### 7.3 三种假验证不算证据

- “代码看起来没问题”；
- “测试文件存在”；
- “上一轮曾经通过”。

## 8. 多轮评审：怎么收敛，别把返工当严谨

多个 AI（子代理、审查者、下一轮会话）给不同意见是常态。要防的是**没有新增证据的重复推翻**。

### 8.1 每条意见先做映射与分档

把每条意见映射到：**需求 / 代码 / 测试 / 证据**。映射不上任何一项的，不做。再分四档：

| 档 | 处理 |
|---|---|
| **真实缺陷** | 必须修复 |
| **必要修复**（不修会出事 / 破门禁） | 必须修复 |
| **可选优化** | 默认**不改**（可记录在刻意未改，说明不改理由） |
| **个人偏好** | 不做 |

**甄别与回复要求**：
- 审查员评论不一定对，必须根据证据标准独立复核（可达路径 + 真实测试）；
- 驳回必须写明依据（哪一点 + 哪条证据 + 为什么不成立）；
- **必回的是回音，不是照办**：只要是有实质内容的评审评论，**必须在 Issue / PR 上回复一条交代**，严禁静默跳过。

### 8.2 不按人数或投票定对错

- **AI 数量、投票结果都不是证据**（“人数不是证据”）；
- 审查意见一致时更要保持警惕，确认是否共享了未核验的前提；
- 语义型代码（日期边界、统计计算、四舍五入）必须附可复现的断言或测试输出，不许凭感觉下结论。

### 8.3 什么时候可以重开已验收的问题

**只有四种触发**：
1. 出现**新证据**；
2. 出现**可复现的缺陷**；
3. 发现**遗漏的需求**；
4. 发现**明确的约束冲突**。

“换个写法更优雅”不是重开条件。

### 8.4 重试上限

同一问题连续失败 **3 次** ⇒ **停止该循环**：
整理已尝试方案、各自证据、失败原因与剩余风险，升级给人决策。

## 9. 测试：绿了不等于对

### 9.1 禁止让测试变绿的手法

- 删除有价值的测试；
- 降低断言标准；
- 改预期结果迎合错误实现；
- 用 `assumeTrue` 让关键回归在环境不满足时静默跳过（本仓 P5 教训）；
- 隐藏失败输出或吞掉异常；
- 用不真实的 Mock 替代真实的端到端行为。

### 9.2 测试盲区必须说明

现有测试无法覆盖全部路径时，必须如实说明盲区与潜在风险。

### 9.3 门禁本身要自证

新增自动化门禁后，将实现恢复到错误状态，确认门禁**变红**；未做这一步的，只能算写了个脚本，不算有效门禁。

---

## 10. 隐私与数据安全额外边界

- **生产代码零日志**：`app/src/` 严禁出现任何 `Log.d`、`Log.i` 或 `println`；
- **本地优先**：离线状态下全部核心功能必须稳定持久化；
- **真实数据安全**：测试必须使用虚构合成数据，严禁引入真实用户数据；
- **凭据隔离**：严禁把 `local.properties`、`google-services.json`、`keystore.properties`、签名秘钥提交进 Git。

---

## 11. 什么时候必须停下来

出现下列情形，**暂停高风险修改并升级给人决策**：
1. 关键业务规则存在无法解决的冲突；
2. 必要的权限、测试环境或工具链不可用；
3. 同一问题达到重试上限（连续 3 次失败）；
4. 修改涉及未授权的破坏性操作（删库、删表、强制推送、批量删除 Issue）；
5. 新发现的问题可能推翻既有架构或 ADR；
6. 继续推进会破坏用户已有的未提交修改。

**暂停 ≠ 放弃任务**：整理已有证据与剩余风险，在不受阻塞的安全范围内继续推进。

## 12. 交付：反虚假完成

最终交付成果必须分五类汇报，**不得合并**：

| 类 | 内容 |
|---|---|
| **A** | 已完成**且通过对应验证**的工作 |
| **B** | 已实施**但尚未充分验证**的工作 |
| **C** | 尚未完成 / 被阻塞 / 验证失败的工作 |
| **D** | 仅为建议、**尚未实施**的内容 |
| **E** | 尚未消除的**风险与测试盲区** |

**禁止**：把“计划已制定”写成“已完成”，把“建议已提出”写成“已修复”，把“局部通过”写成“系统已安全”，把〔推断〕写成〔已验证〕。

## 13. 交付前自检（10 问）

1. 我报的每个关键结论是〔已验证〕/〔推断〕/〔未知〕？标对了吗？
2. 每个〔已验证〕都附了别人能复核的路径、命令和输出吗？
3. 有没有把〔推断〕写成事实？有没有把〔未知〕补成看似合理的答案？
4. 冲突的来源都记下了吗？裁决依据是什么？
5. 测试是跑过的还是只存在文件？跑的那次是本轮代码吗？
6. 有没有夹带无关改动？用户原有的修改还在吗？
7. 我引用的历史结论，这轮复核过吗？
8. 中间产物彻底清理干净了吗？仓库外桌面目录连同目录壳一起删了吗？
9. 撞到重试上限或停止条件了吗？该升级给人了吗？
10. 交付的 A/B/C/D/E 分类如实吗？有没有把 D 写成 A？

## 14. 维护规则

- 本规范可以根据实践教训持续修订；每次修订写清改动点、理由与门禁同步；
- 门禁：`scripts/governance-rules.test.mjs` 锁死规范本体、核心要素、三档主张、测试五态、A~E 交付分类与防形式主义豁免段。
